# ADR-003: 한마디를 카테고리(`phrase_sets`) 단위로 DB에 두고 API로 내보낸다

- 상태: 채택 (H-3: 2026-11-28 `cafe`·`convenience`·`transit` 각 6개를 초안으로 DB에만 추가, 일본어 검수 대기. FE 화면에는 아직 보이지 않음. 고르기 화면 위치는 FE 결정 H-4)
- 날짜: 2026-11-27
- 결정한 사람: 태원 (BE)
- 고치는 결정: ADR-001 결정 7의 "한마디 문장 API는 만들지 않는다", ADR-002 결정 4의 "`set_code`는 뺀다"
- 관련: [ERD](../design/erd.md), [API 명세](../design/api.md) §4·§6·§7

## 배경

지금 한마디 6개는 해커톤 현장용이고, FE가 빌드 때 `content/phrases.json`을 번들에 넣어 쓴다. 앱은 한 장소에서만 쓰는 것이 아니다. 편의점, 화장실, 일상 회화처럼 상황별 한마디를 고르게 하려면 카테고리가 필요하다. 문장을 바꿀 때마다 FE를 다시 빌드·배포하는 구조는 이 확장에 맞지 않는다.

반면 제약도 있다.
- 문장은 일본어 검수가 끝난 고정 문장만 쓴다(런타임 생성 금지). 카테고리별 문장은 아직 없다.
- 카드는 탭 후 1초 안에 떠야 한다.
- 코드 프리즈 2026-11-29 17:00.

## 결정

1. `phrase_sets`(code PK, name_ja, sort_order, is_active) 테이블을 만들고 `phrases.set_code`를 FK로 둔다.
2. 지금은 `hackathon` 카테고리 하나만 시드한다. 다른 카테고리는 **보류(H-3)**. 검수된 문장이 준비되면 `content/`에 데이터만 추가하고 `seed.py`를 돌린다. 스키마·코드 변경은 없다.
3. 원본은 계속 `content/` 파일이다. `content/phrase_sets.json`을 새로 두고, `phrases.json` 항목에는 나중에 `set` 필드를 더한다(없으면 `hackathon`). 지금 `phrases.json`은 바꾸지 않는다.
4. 읽기 전용 API를 둔다: `GET /api/phrase-sets`, `GET /api/phrases?set_code=`. 공개 콘텐츠라 인증이 없고, `Cache-Control: public, max-age=300`을 단다.
5. **진행도와 완료는 카테고리별**이다. 도장 응답의 `progress`는 활성 카테고리 전부의 `{set_code, count, total, completed}` 배열이다.
6. 한마디 `id`는 카테고리가 달라도 전체에서 유일하다. 도장 PK `(user_id, phrase_id)`는 그대로다.
7. FE 사용 방식은 제안만 한다: 로그인 직후 한 번 받아 두고, 실패하면 번들 `phrases.json`을 쓴다. 카테고리 고르기 화면의 위치는 FE가 정한다(H-4).

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| A. 지금처럼 번들만 (API 없음), `set_code` 컬럼만 준비 | 프리즈 전 위험은 가장 작다. 하지만 카테고리가 생길 때마다 FE 재배포가 필요하고, 서버가 콘텐츠의 원본 역할을 못 한다 |
| B. `phrases.set_code` 문자열 컬럼만 (카테고리 테이블 없음) | 카테고리 이름(일본어)·순서·활성 여부를 둘 곳이 없다. 이것들이 FE 코드에 하드코딩된다 |
| C. 카드 탭마다 `GET /api/phrases/{id}` | 행사장 와이파이에서 1초 기준을 못 지킬 수 있다 |
| D. 진행도를 전체 하나로 | 카테고리가 늘면 "편의점 다 모음" 같은 단위 완성이 없어진다. 전체 완료는 FE가 배열로 계산할 수 있다 |
| E. 한마디 id를 `(set_code, id)` 복합 키로 | 도장 PK와 FE의 `phraseId` 하나짜리 모델이 바뀐다. 전역 유일 id로 충분하다 |

## 결과와 트레이드오프

- 좋아지는 점: 카테고리 추가가 콘텐츠 작업만으로 끝난다. FE는 문장 변경 때 재배포하지 않아도 된다(API를 쓰기 시작한 뒤).
- 비용: 테이블 1개, 엔드포인트 2개. FE는 한마디 로딩 경로가 둘(API, 번들 대비)이 된다.
- 위험: FE가 API로 바꾸기 전까지는 번들과 DB가 같은 파일에서 나오므로 어긋나지 않는다. API로 바꾼 뒤에는 DB가 기준이고 번들은 대비용 사본이다.
- 팀 규칙 영향: frontend/CLAUDE.md의 "한마디 데이터는 번들에 넣어 쓴다"를 바꾸는 것을 FE에 제안한다. 루트 CLAUDE.md의 "서울 장소 한마디는 만들지 않는다"는 카테고리 콘텐츠가 보류라 지금은 충돌하지 않는다. 실제 장소 카테고리를 넣기로 할 때 팀이 그 규칙을 고친다.
