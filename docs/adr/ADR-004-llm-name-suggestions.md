# ADR-004: 한국식 이름 후보를 BE가 LLM(Gemini Flash)으로 만들고, 실패하면 FE 임시 규칙으로 대신한다

- 상태: 채택 (2026-11-27 FE PR #2에 맞춰 입력·출력 모양 갱신)
- 날짜: 2026-11-27
- 결정한 사람: 태원 (BE). AI 이름 짓기는 **BE 담당**으로 팀에서 정리함
- 고치는 결정: ADR-001 결정 7의 "이름 후보 API는 만들지 않는다", ADR-002의 "서버는 고른 이름 문자열만 저장"(저장은 그대로, 후보 생성이 서버로 감)
- 관련: [API 명세](../design/api.md) §8, [구성 계획](../design/backend-architecture.md) §4.3·§6, [ERD](../design/erd.md) `name_suggestions`

## 배경

FE `names.ts`는 규칙으로 후보를 만든다: 한자는 한국 한자음, 가나는 소리대로 옮기고, 나머지는 인기 한국 이름 목록에서 채운다. 빠르고 오프라인에서도 되지만 후보가 기계적이다. 세 번째 후보가 이름과 상관없는 인기 이름이 되기도 한다. 한국식 이름 도장은 MVP의 핵심 경험이라 후보 품질을 올리고 싶다.

FE PR #2(2026-11-27 머지)에서 이름 짓기를 끼우는 자리가 생겼다.

```ts
type NameCandidate = { name: string; note?: string }
type NameGenerator = (fullName: string) => Promise<NameCandidate[]>   // 성+이름 전체를 받음
```

지금은 임시 규칙(`temporaryNameGenerator`)이 들어 있고, AI 구현이 오면 `main.tsx`에서 바꿔 끼운다. 짓는 규칙은 "성에서 한 글자 + 이름을 한국 이름처럼"으로 FE 주석에 적혀 있다. 설정 화면은 입력이 멈추고 500ms 뒤에 이름 짓기를 부르고(디바운스), 한글 입력은 부르지 않고 그대로 쓴다.

제약:
- "1분 안에 도장 하나" 완료 기준. 이름 단계에서 막히면 안 된다.
- 행사장 네트워크가 불안정할 수 있다.
- 팀 규칙 "런타임에 LLM으로 **문장**을 생성하지 않는다"는 한마디 문장에 대한 것이다. 이름 후보는 한마디가 아니다.

## 결정

1. `POST /api/names/suggest {ja_name}` → `{candidates: [{name, note}]}` 3개. 입력은 **성+이름 전체**, 출력 필드는 FE `NameCandidate`와 같은 이름이다. 로그인한 사용자만 부를 수 있다.
2. 짓는 규칙: 성에서 한 글자를 골라 한국 성처럼(가능하면 실제 있는 한국 성), 이름은 한국 이름처럼. 후보 3개는 서로 다른 방식(한자음 / 소리 / 뜻·인상)으로. 성이 없으면 이름만으로. 자세한 내용은 구성 계획 §6.
3. LLM은 Gemini Flash 계열, SDK는 `google-genai`(새 의존성, 승인됨). 모델 이름은 `GEMINI_MODEL` 설정값.
4. JSON 스키마 출력을 쓰고, 서버가 결과를 **엄격히 검증**한다: `name` `^[가-힣]{1,10}$`, 서로 다름, 정확히 3개, `note` 1~40자. 어기면 저장하지 않고 503.
5. 서버 시간 제한 2.5초. 시간 초과·오류·키 없음·검증 실패는 모두 503 `name_suggest_unavailable`.
6. **대비 경로는 FE**: 서버를 부르는 `NameGenerator` 구현이 503·3초 초과·네트워크 오류일 때 `temporaryNameGenerator`로 대신한다. 설정 화면 코드는 바뀌지 않는다.
7. 정규화한 입력(NFKC → trim → 연속 공백 하나로)을 키로 `name_suggestions`에 결과를 캐시한다. 같은 이름은 같은 후보가 나오고, 두 번째부터 LLM을 부르지 않는다.
8. 일본어 이름과 LLM 응답 원문은 로그에 남기지 않는다. 캐시는 `reset.py --names`로 비울 수 있다.
9. 고른 이름 저장은 그대로 `PUT /api/me/profile`이다. 이름 패스(`""`)도 여기로 보낸다.

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| A. 지금처럼 FE 규칙만 | 후보 품질 문제가 남는다 |
| B. FE에서 Gemini를 직접 호출 | API 키가 브라우저에 노출된다 |
| C. 대비 규칙을 서버로 옮기기 (Python 재구현) | `names.ts`와 한자표를 두 벌 유지해야 한다. 네트워크가 끊기면 서버 대비도 못 쓴다. FE 대비가 오프라인까지 덮는다 |
| D. 출력을 `{hangul, kana, meaning_ja}`로 (처음 설계) | FE `NameCandidate {name, note}`와 달라 FE에 변환이 생긴다. 읽는 법(가나)은 FE가 보여 주지 않는다 |
| E. 이름(마지막 단어)만 입력 (처음 설계) | "성에서 한 글자" 규칙을 쓸 수 없다. FE는 전체 이름을 넘긴다 |
| F. 버튼을 눌렀을 때만 호출 | 호출 수는 줄지만 FE가 이미 디바운스 방식으로 화면을 만들었다. 캐시와 30자 제한으로 비용을 감당한다 |
| G. 캐시 없음 | 같은 이름을 다시 입력하면 후보가 바뀌어 혼란스럽고, 디바운스 때문에 호출이 많아진다 |
| H. 다른 LLM(Claude 등) | 팀이 Gemini Flash로 정했다. `llm/base.py`의 `NameGenerator` 인터페이스 뒤에 있어서 나중에 바꿀 수 있다 |
| I. 사용자별 호출 제한 | 동시 사용자 수십 명, 인증 필수, 캐시, 입력 30자 제한이면 남용 위험이 작다. 단순함을 고른다 |

## 결과와 트레이드오프

- 좋아지는 점: 성과 이름을 모두 살린 자연스러운 후보와 일본어 설명(`note`). FE는 `main.tsx` 한 줄 바꿔 끼우면 된다.
- 비용: 외부 의존(키, 서버의 외부 HTTPS), 새 의존성 하나, 테이블 하나.
- 지연: 처음 보는 이름은 1~3초 더 걸린다. 캐시된 이름이나 대비 경로는 바로 나온다. FE는 기다리는 동안 동물을 고를 수 있다.
- 호출 수: 디바운스 때문에 입력 중간값(예: 성만 입력한 상태)도 LLM을 부를 수 있다. 캐시 키가 중간값도 저장하므로 같은 중간값은 다시 부르지 않는다.
- 개인 정보: 사용자의 일본어 이름(심사위원 실명일 수 있음, 성 포함)이 Google로 전송된다. 팀이 알고 동의해야 하며, 필요하면 설정 화면에 일본어 안내를 넣는 것을 FE에 제안한다.
- 비결정성: 같은 입력이라도 처음 생성 결과는 모델에 따라 다르다. 캐시가 이후 결과를 고정한다.
- 배포: `GEMINI_API_KEY`, `GEMINI_MODEL`을 `compose.prod.yml` env에 넣도록 현우 님께 제안한다. 키가 없어도 앱은 대비 경로로 돈다.
